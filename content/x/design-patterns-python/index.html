Reusable solutions
to recurring problems.

A design pattern is a tried template for a problem that keeps showing up in software design — not code you copy, but a shape you recognise. This manual catalogues all 23 classic patterns with a tight Python implementation and, crucially, a note on the Pythonic shortcut, since several patterns dissolve into a single language feature here.

FAMILY 01

Creational

These patterns abstract the instantiation process, letting a system stay independent of how its objects are created, composed, and represented.

01

Singleton

family · creational

Intent — ensure a class has only one instance and give the world a single point of access to it.

Use when
  • Exactly one object must coordinate actions — a config store, a connection pool, a logger.
  • You need a single shared resource and a global, controlled access point to it.
singleton.py 
class Singleton:
    _instance = None

    def __new__(cls, *args, **kwargs):
        if cls._instance is None:
            cls._instance = super().__new__(cls)
        return cls._instance

a = Singleton()
b = Singleton()
assert a is b          # same object every time
Py

Pythonic note: a plain module is already a singleton — its globals are shared on import. Reach for a class-based singleton only when you need lazy init or inheritance; otherwise a module (or a @functools.cache'd factory) is cleaner.

02

Factory Method

aka · virtual constructor

Intent — define an interface for creating an object, but let subclasses decide which concrete class to instantiate.

Use when
  • A class can't anticipate the type of objects it must create.
  • You want subclasses to specify the products they build.
factory_method.py 
from abc import ABC, abstractmethod

class Button(ABC):
    @abstractmethod
    def render(self) -> str: ...

class HTMLButton(Button):
    def render(self): return "<button>OK</button>"

class WinButton(Button):
    def render(self): return "[ OK ]"

class Dialog(ABC):
    @abstractmethod
    def create_button(self) -> Button: ...   # the factory method

    def render(self):                         # uses the product
        return self.create_button().render()

class WebDialog(Dialog):
    def create_button(self): return HTMLButton()

print(WebDialog().render())   # <button>OK</button>
Py

Pythonic note: since classes are first-class objects, you can often just pass the class itself (or a callable) as a parameter instead of subclassing a creator.

03

Abstract Factory

aka · kit

Intent — provide an interface for creating families of related objects without specifying their concrete classes.

Use when
  • Products must be used together and you want to enforce that consistency (e.g. a whole UI theme).
  • You want to swap an entire family of objects in one move.
abstract_factory.py 
from abc import ABC, abstractmethod

class Button(ABC):   ...
class Checkbox(ABC): ...

class GUIFactory(ABC):
    @abstractmethod
    def button(self) -> Button: ...
    @abstractmethod
    def checkbox(self) -> Checkbox: ...

class MacFactory(GUIFactory):
    def button(self):   return MacButton()
    def checkbox(self): return MacCheckbox()

class WinFactory(GUIFactory):
    def button(self):   return WinButton()
    def checkbox(self): return WinCheckbox()

def build_ui(factory: GUIFactory):
    return factory.button(), factory.checkbox()
Py

Pythonic note: Factory Method makes one product; Abstract Factory makes a coordinated set. A module exposing several factory functions is a lightweight stand-in.

04

Builder

family · creational

Intent — separate the construction of a complex object from its representation so the same process can yield different results.

Use when
  • An object needs many optional parts or a long, step-by-step assembly.
  • You want a readable, fluent construction API instead of a giant constructor.
builder.py 
class Pizza:
    def __init__(self):
        self.toppings = []

class PizzaBuilder:
    def __init__(self):
        self.pizza = Pizza()

    def add(self, topping):
        self.pizza.toppings.append(topping)
        return self            # return self => fluent chaining

    def build(self):
        return self.pizza

pizza = PizzaBuilder().add("mozzarella").add("basil").build()
print(pizza.toppings)          # ['mozzarella', 'basil']
Py

Pythonic note: keyword arguments with defaults and @dataclass cover most "many optional fields" cases. Save a true Builder for genuinely multi-step or validated assembly.

05

Prototype

aka · clone

Intent — create new objects by copying a fully configured existing instance rather than building from scratch.

Use when
  • Construction is expensive and you already have a configured exemplar.
  • You want to avoid a parallel hierarchy of factory classes.
prototype.py 
import copy

class Document:
    def __init__(self, title, sections):
        self.title = title
        self.sections = sections

    def clone(self):
        return copy.deepcopy(self)    # independent deep copy

template = Document("Report", ["intro", "body"])
draft = template.clone()
draft.title = "Q3 Report"             # original untouched
Py

Pythonic note: the standard library is the pattern — copy.copy (shallow) and copy.deepcopy (deep). Customise via __copy__ / __deepcopy__.

FAMILY 02

Structural

These patterns describe how classes and objects are composed to form larger structures, keeping those structures flexible and efficient as they grow.

06

Adapter

aka · wrapper

Intent — convert the interface of a class into another interface clients expect, letting incompatible classes work together.

Use when
  • You want to use an existing class but its interface doesn't match yours.
  • You're integrating a third-party or legacy API you can't change.
adapter.py 
class EuropeanSocket:           # the adaptee
    def voltage(self): return 230

class USADevice:                # expects ~120V via .volts()
    def run(self, source):
        print("running at", source.volts())

class SocketAdapter:            # adapts European -> USADevice
    def __init__(self, socket):
        self._socket = socket
    def volts(self):
        return self._socket.voltage() // 2

USADevice().run(SocketAdapter(EuropeanSocket()))   # running at 115
Py

Pythonic note: duck typing means you only need to match the methods actually called, not implement a full interface. That makes adapters tiny.

07

Bridge

family · structural

Intent — decouple an abstraction from its implementation so the two can vary independently.

Use when
  • You'd otherwise get a class explosion from crossing two dimensions (e.g. shapes × renderers).
  • Both the abstraction and implementation should be extensible by subclassing.
bridge.py 
from abc import ABC, abstractmethod

class Device(ABC):              # the implementation side
    @abstractmethod
    def enable(self): ...

class TV(Device):
    def enable(self): print("TV on")

class Radio(Device):
    def enable(self): print("Radio on")

class Remote:                   # the abstraction side
    def __init__(self, device: Device):
        self.device = device    # the bridge
    def power(self):
        self.device.enable()

Remote(TV()).power()            # TV on
Remote(Radio()).power()         # Radio on
Py

Pythonic note: Bridge is composition over inheritance, planned up front. The remote "has-a" device rather than "is-a" specific remote subclass.

08

Composite

aka · object tree

Intent — compose objects into tree structures and let clients treat individual objects and compositions uniformly.

Use when
  • You have a part-whole hierarchy — files & folders, UI widgets, org charts.
  • Clients should ignore the difference between a leaf and a container.
composite.py 
from abc import ABC, abstractmethod

class Component(ABC):
    @abstractmethod
    def price(self) -> float: ...

class Product(Component):        # leaf
    def __init__(self, cost): self.cost = cost
    def price(self): return self.cost

class Box(Component):            # composite
    def __init__(self): self.items = []
    def add(self, item): self.items.append(item)
    def price(self): return sum(i.price() for i in self.items)

box = Box()
box.add(Product(10))
inner = Box(); inner.add(Product(5)); box.add(inner)
print(box.price())               # 15
Py

Pythonic note: the leaf and composite share one method name (price), so recursion "just works" — no type checks needed at the call site.

09

Decorator

aka · wrapper

Intent — attach additional responsibilities to an object dynamically by wrapping it, a flexible alternative to subclassing.

Use when
  • You want to add behavior to individual objects, not the whole class.
  • Subclassing for every combination of features would explode.
decorator.py 
class Coffee:
    def cost(self): return 2.0
    def label(self): return "coffee"

class MilkDecorator:             # wraps any coffee-like object
    def __init__(self, drink): self._drink = drink
    def cost(self):  return self._drink.cost() + 0.5
    def label(self): return self._drink.label() + " + milk"

class SugarDecorator:
    def __init__(self, drink): self._drink = drink
    def cost(self):  return self._drink.cost() + 0.2
    def label(self): return self._drink.label() + " + sugar"

order = SugarDecorator(MilkDecorator(Coffee()))
print(order.label(), order.cost())   # coffee + milk + sugar 2.7
Py

Pythonic note: don't confuse this with Python's @decorator syntax — that's a language-level function wrapper inspired by the same idea. Both wrap to add behavior.

10

Facade

family · structural

Intent — provide a unified, simplified interface to a set of interfaces in a subsystem.

Use when
  • A subsystem is complex and most clients only need the common path.
  • You want to decouple clients from many moving internal parts.
facade.py 
class CPU:    def boot(self):  print("cpu: boot")
class Memory: def load(self):  print("mem: load")
class Disk:   def read(self):  print("disk: read")

class Computer:                  # the facade
    def __init__(self):
        self._cpu, self._mem, self._disk = CPU(), Memory(), Disk()
    def start(self):             # one simple call hides the dance
        self._cpu.boot()
        self._disk.read()
        self._mem.load()

Computer().start()
Py

Pythonic note: a module's public functions often are a facade over private helpers — e.g. requests.get() hiding sessions, adapters, and pools.

11

Flyweight

aka · cache / shared object

Intent — use sharing to support large numbers of fine-grained objects efficiently by separating shared (intrinsic) from unique (extrinsic) state.

Use when
  • An app spawns a huge number of objects with lots of duplicated state.
  • Memory cost matters and the duplicated state can be shared.
flyweight.py 
class TreeType:                  # intrinsic, shared state
    def __init__(self, name, texture):
        self.name, self.texture = name, texture

class TreeFactory:
    _pool = {}
    @classmethod
    def get(cls, name, texture):
        key = (name, texture)
        if key not in cls._pool:
            cls._pool[key] = TreeType(name, texture)
        return cls._pool[key]     # reuse, never duplicate

oak_a = TreeFactory.get("oak", "bark.png")
oak_b = TreeFactory.get("oak", "bark.png")
assert oak_a is oak_b            # one shared instance; (x, y) stays extrinsic
Py

Pythonic note: Python already interns small ints and short strings. For your own objects, a dict pool or @functools.cache on a factory gives you flyweight behavior for free.

12

Proxy

aka · surrogate

Intent — provide a placeholder for another object to control access to it — for laziness, caching, logging, or protection.

Use when
  • You want lazy/expensive initialization (virtual proxy).
  • You need access control, caching, or logging around an object.
proxy.py 
class Image:                     # the real, expensive object
    def __init__(self, path):
        self.path = path
        print(f"loading {path}…")   # heavy work in ctor
    def display(self): print(f"showing {self.path}")

class LazyImage:                 # virtual proxy — same interface
    def __init__(self, path):
        self.path = path
        self._real = None
    def display(self):
        if self._real is None:       # load only on first use
            self._real = Image(self.path)
        self._real.display()

img = LazyImage("cat.png")       # nothing loaded yet
img.display()                    # loads, then shows
Py

Pythonic note: override __getattr__ to forward unknown attributes to the wrapped object, and you get a transparent proxy with almost no boilerplate.

FAMILY 03

Behavioral

These patterns are concerned with algorithms and the assignment of responsibilities between objects — the patterns of communication that emerge between them.

13

Chain of Responsibility

family · behavioral

Intent — pass a request along a chain of handlers until one of them handles it, decoupling sender from receiver.

Use when
  • More than one object may handle a request and the handler isn't known up front.
  • You want to issue a request without hard-coding the receiver — e.g. middleware, event bubbling.
chain.py 
from abc import ABC, abstractmethod

class Handler(ABC):
    def __init__(self): self._next = None
    def set_next(self, handler):
        self._next = handler
        return handler           # enables chaining
    def handle(self, level):
        if self._next:
            return self._next.handle(level)
        return None

class InfoHandler(Handler):
    def handle(self, level):
        if level == "info": return "logged info"
        return super().handle(level)

class ErrorHandler(Handler):
    def handle(self, level):
        if level == "error": return "alerted on error"
        return super().handle(level)

chain = InfoHandler()
chain.set_next(ErrorHandler())
print(chain.handle("error"))     # alerted on error
Py

Pythonic note: a simple list of callables you loop over — stopping at the first truthy return — is a flat, very readable version of the same idea.

14

Command

aka · action / transaction

Intent — encapsulate a request as an object, letting you parameterize, queue, log, and undo operations.

Use when
  • You need undo/redo, queues, or a history of operations.
  • You want to decouple the object that invokes from the one that performs.
command.py 
from abc import ABC, abstractmethod

class Command(ABC):
    @abstractmethod
    def execute(self): ...

class Light:
    def on(self):  print("light on")
    def off(self): print("light off")

class LightOnCommand(Command):
    def __init__(self, light): self.light = light
    def execute(self): self.light.on()

class Remote:                    # the invoker
    def __init__(self): self.history = []
    def submit(self, command):
        command.execute()
        self.history.append(command)

Remote().submit(LightOnCommand(Light()))
Py

Pythonic note: a closure or functools.partial captures "an action plus its args" in one callable — often all the Command you need unless you also want undo.

15

Interpreter

family · behavioral

Intent — given a language, define a representation for its grammar and an interpreter that uses it to evaluate sentences.

Use when
  • You have a simple, well-defined grammar to evaluate (rules, filters, math).
  • Efficiency isn't critical and the grammar is small enough to map to classes.
interpreter.py 
class Number:
    def __init__(self, value): self.value = value
    def interpret(self): return self.value

class Add:
    def __init__(self, left, right):
        self.left, self.right = left, right
    def interpret(self):
        return self.left.interpret() + self.right.interpret()

class Mul:
    def __init__(self, left, right):
        self.left, self.right = left, right
    def interpret(self):
        return self.left.interpret() * self.right.interpret()

# (2 + 3) * 4
tree = Mul(Add(Number(2), Number(3)), Number(4))
print(tree.interpret())          # 20
Py

Pythonic note: for anything beyond a toy grammar, reach for a real parser (ast, lark, pyparsing). Hand-rolled Interpreter trees get unwieldy fast.

16

Iterator

aka · cursor

Intent — provide a way to access the elements of a collection sequentially without exposing its underlying representation.

Use when
  • You want a uniform traversal API across different collection types.
  • You need multiple, independent traversals of the same structure.
iterator.py 
class Countdown:
    def __init__(self, start): self.start = start

    def __iter__(self):          # generator = iterator, for free
        n = self.start
        while n > 0:
            yield n
            n -= 1

for x in Countdown(3):
    print(x)                     # 3, 2, 1
Py

Pythonic note: this is the pattern Python builds in. Implement __iter__ (often as a generator) and the whole language — for, comprehensions, in, unpacking — cooperates automatically.

17

Mediator

aka · intermediary

Intent — define an object that encapsulates how a set of objects interact, promoting loose coupling by keeping them from referring to each other directly.

Use when
  • Many objects communicate in complex, tangled ways (a "spaghetti" of references).
  • You want to centralize and reuse interaction logic.
mediator.py 
class ChatRoom:                  # the mediator
    def __init__(self): self.users = []
    def join(self, user):
        self.users.append(user); user.room = self
    def broadcast(self, sender, msg):
        for u in self.users:
            if u is not sender:
                u.receive(sender.name, msg)

class User:
    def __init__(self, name): self.name, self.room = name, None
    def send(self, msg):    self.room.broadcast(self, msg)
    def receive(self, who, msg): print(f"{self.name} got '{msg}' from {who}")

room = ChatRoom()
a, b = User("Ada"), User("Bon")
room.join(a); room.join(b)
a.send("hi")                     # Bon got 'hi' from Ada
Py

Pythonic note: Mediator centralizes who-talks-to-whom; Observer centralizes broadcast on change. They often appear together in event systems.

18

Memento

aka · snapshot / token

Intent — capture an object's internal state so it can be restored later, without violating encapsulation.

Use when
  • You need snapshots for undo, rollback, or checkpoints.
  • Exposing the object's internals to grab that state would break encapsulation.
memento.py 
class Memento:
    def __init__(self, state): self._state = state   # opaque to others

class Editor:
    def __init__(self): self.text = ""
    def type(self, s): self.text += s
    def save(self):    return Memento(self.text)     # create snapshot
    def restore(self, m): self.text = m._state       # roll back

editor = Editor()
editor.type("hello")
checkpoint = editor.save()
editor.type(" world")
editor.restore(checkpoint)
print(editor.text)               # hello
Py

Pythonic note: copy.deepcopy(obj.__dict__) or pickle can serve as a quick memento for whole-object snapshots when fields are simple.

19

Observer

aka · publish / subscribe

Intent — define a one-to-many dependency so that when one object changes state, all its dependents are notified automatically.

Use when
  • A change to one object requires changing others, and you don't know how many.
  • You want event-driven decoupling between a source and its listeners.
observer.py 
class Subject:                   # the publisher
    def __init__(self): self._observers = []
    def subscribe(self, fn):   self._observers.append(fn)
    def unsubscribe(self, fn): self._observers.remove(fn)
    def notify(self, data):
        for fn in self._observers:
            fn(data)

def email_alert(data): print("email:", data)
def sms_alert(data):   print("sms:", data)

news = Subject()
news.subscribe(email_alert)
news.subscribe(sms_alert)
news.notify("server down")       # both fire
Py

Pythonic note: subscribers can be plain functions — no Observer base class required. This callback-list form powers most GUI and async event handling.

20

State

aka · objects for states

Intent — allow an object to alter its behavior when its internal state changes — it appears to change its class.

Use when
  • An object's behavior depends on its state and must change at runtime.
  • You have sprawling conditionals keyed on a state variable.
state.py 
from abc import ABC, abstractmethod

class State(ABC):
    @abstractmethod
    def next(self): ...
    @abstractmethod
    def signal(self): ...

class Red(State):
    def next(self):   return Green()
    def signal(self): return "STOP"

class Green(State):
    def next(self):   return Red()
    def signal(self): return "GO"

class TrafficLight:
    def __init__(self): self.state = Red()
    def change(self):   self.state = self.state.next()
    def show(self):     return self.state.signal()

light = TrafficLight()
print(light.show())              # STOP
light.change()
print(light.show())              # GO
Py

Pythonic note: State and Strategy share a structure; the difference is intent — State objects know about and trigger transitions to each other, strategies don't.

21

Strategy

aka · policy

Intent — define a family of algorithms, encapsulate each, and make them interchangeable at runtime.

Use when
  • You have several ways to do one thing and want to pick at runtime.
  • You want to strip a bulky conditional that selects behavior.
strategy.py 
# In Python, strategies are usually just functions.
def by_length(s):       return len(s)
def alphabetical(s):    return s.lower()

def sort_words(words, strategy):
    return sorted(words, key=strategy)   # inject the algorithm

words = ["pear", "Fig", "banana"]
print(sort_words(words, by_length))      # ['Fig', 'pear', 'banana']
print(sort_words(words, alphabetical))   # ['banana', 'Fig', 'pear']
Py

Pythonic note: first-class functions collapse the classic Strategy hierarchy into a single parameter. sorted(..., key=fn) is Strategy in the standard library.

22

Template Method

family · behavioral

Intent — define the skeleton of an algorithm in a method, deferring some steps to subclasses without changing the algorithm's structure.

Use when
  • Several variants share an overall workflow but differ in specific steps.
  • You want to lock the invariant order while letting steps vary.
template_method.py 
from abc import ABC, abstractmethod

class Report(ABC):
    def generate(self):          # the template method (fixed order)
        self.header()
        self.body()              # the varying step
        self.footer()
    def header(self): print("=== REPORT ===")
    @abstractmethod
    def body(self): ...
    def footer(self): print("=== END ===")

class SalesReport(Report):
    def body(self): print("rows of sales data")

SalesReport().generate()
Py

Pythonic note: Template Method uses inheritance to inject steps; Strategy uses composition. If steps need to vary independently, prefer passing callables.

23

Visitor

aka · double dispatch

Intent — represent an operation to perform on the elements of an object structure, letting you add new operations without changing the element classes.

Use when
  • You frequently add operations over a stable class hierarchy.
  • Unrelated operations would otherwise pollute the element classes.
visitor.py 
from abc import ABC, abstractmethod

class Shape(ABC):
    @abstractmethod
    def accept(self, visitor): ...

class Circle(Shape):
    def __init__(self, r): self.r = r
    def accept(self, v): return v.visit_circle(self)

class Square(Shape):
    def __init__(self, side): self.side = side
    def accept(self, v): return v.visit_square(self)

class AreaVisitor:               # a new operation, added externally
    def visit_circle(self, c): return 3.14159 * c.r ** 2
    def visit_square(self, s): return s.side ** 2

shapes = [Circle(2), Square(3)]
area = AreaVisitor()
print([s.accept(area) for s in shapes])   # [12.566…, 9]
Py

Pythonic note: functools.singledispatch gives you type-based operation dispatch without the accept boilerplate — a far more Pythonic Visitor for many cases.

Before you reach for a pattern

// the meta-rules that matter more than any single pattern
Pattern ≠ goal
Patterns are vocabulary for problems you already have. Don't go looking for a place to use one — that's how over-engineering starts.
Composition > inheritance
Most structural and behavioral patterns are just "prefer has-a over is-a" in different costumes. Reach for objects holding objects.
Program to an interface
Depend on what an object does (its methods), not what it is. In Python, duck typing makes this nearly free.
Many GoF patterns dissolve in Python
First-class functions, generators, decorators, copy, and modules already are Strategy, Iterator, Decorator, Prototype, and Singleton. Use the language first.
Encapsulate what varies
Find the part of your design that changes and isolate it. Almost every pattern is one application of this single idea.
Keep it the simplest thing that works
A function beats a class; a class beats a hierarchy. Escalate to a full pattern only when the simpler form genuinely hurts.
